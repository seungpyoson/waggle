## Acceptance contract

The release must demonstrate, on this user's local subscription-authenticated runtimes:

1. Claude→Codex→Claude, Codex→Claude→Codex, and Codex A→Codex B→Codex A, with distinct concrete conversations and replies correlated to the original message.
2. Idle recipients start processing without another human prompt, shell command, or manual inbox poll. Busy recipients safely receive later or produce an explicit held/refused result.
3. Participating agents retain normal interactive use. The supported Codex entrypoint is its normal TUI explicitly attached with `--remote unix://<registered endpoint>` to a user-owned App Server. Plain `codex` sessions are not assumed to use that endpoint. Starting a different worker must never be reported as reaching an existing session.
4. Names resolve unambiguously to an exact session incarnation. Two Codex sessions in the same directory cannot share identity. Known history, a live Waggle listener, a PID, or a transcript is insufficient to report runtime readiness.
5. Unknown/dead direct targets fail explicitly. Persisting a message is reported as stored, never runtime-accepted or replied. Offline durable enqueue is an explicitly different operation; it is not silently substituted for direct delivery.
6. Restart before dispatch preserves pending work. Ambiguous acceptance is reconciled from provider evidence or remains explicitly uncertain. No blind retry can duplicate a possibly accepted write-capable request. Stale workers cannot commit receipts for a newer attempt.
7. One bounded ordered queue, explicit backpressure, inherited conversation budgets, and deadlines/stop enforced at Waggle's dispatch boundary. Once a provider may possess input, Waggle cannot promise withdrawal or cessation of native work. Retained input keeps its ordering barrier until evidence resolves it; expiry alone cannot release it. The lifecycle below defines these limits before implementation.
8. Peer messages confer no permission. Runtime policies and inbound controls remain effective, sender identity is derived from a scoped registration, and tokens/credentials are never printed or placed in prompts. No paid API fallback or account rotation is introduced.
9. Build, applicable tests, degraded-state CLI help, native conformance, real-session matrix, and both final reviews pass. Missing environment evidence is not a pass. No merge or deployment is implied by reviewer approval.

The broad execution platform (objectives, work graphs beyond existing tasks, evidence marketplaces, fleet reconstruction, ACP/A2A federation, topology selection) remains future work. Stable identities, durable attempts, and explicit driver capabilities are founding boundaries now.

## Invariant, responsible component, and production evidence

Invariant: a durable message is addressed to one exact runtime incarnation and remains in an explicit state supported by observed native acceptance or a correlated reply. Storage, notification, transport progress, and model response are different facts. Only the per-project broker may transition canonical message/session/attempt state.

The current production path is CLI `send` → broker `handleSend` → name/name-push socket → runtime `handleDelivery` → a second SQLite record → `notifyRecord` → signal file → shell/PreToolUse hook. Bootstrap independently opens the runtime store and marks records surfaced/dismissed before its caller prints them. The broker never observes native input acceptance.

Direct evidence at the base head: `internal/broker/router.go:668` stores before target resolution; `internal/runtime/manager.go:382` writes the second record; `manager.go:483` writes the signal and marks notification; `internal/adapter/bootstrap.go:121` dismisses before returning; `cmd/adapter.go:53` calls Bootstrap before rendering; `cmd/runtime_pull.go:37` marks surfaced before printing. A prior local fixture executed the shipped Claude push hook and observed exit 0, a deleted signal, and top-level `additionalContext`. The current hooks reference does not add that top-level field to context for PreToolUse. The failure is the unsupported field at the installed event and consumption before host evidence; changing the envelope would not establish reliable receipt or idle delivery. The fixture is reported prior local evidence, not live-provider E2E evidence.

Additional confirmed ownership failures: `cmd/start.go:44` enters foreground construction without an ownership check; `internal/broker/broker.go:113,329` unconditionally removes the socket; `cmd/root.go:47-64,136-169` removes socket/PID after health or handshake timeouts. A process may still be alive with a database handle. `internal/messages/store.go:279-301` also mutates receipt-like state when inbox is read. These writers and destructive recovery paths cannot enforce a sole-owner invariant.

The current design cannot enforce the invariant because none of its canonical-state writers owns the native input boundary, and they independently interpret receipt. Fixing names, adding another acknowledgement file, or retrying hooks would retain that split. The structural change removes the intermediate delivery store and hook consumption from the supported messaging path, consolidates scheduling and receipts in the broker, and obtains native facts through driver modules.

## Architecture and authority

Keep Go, SQLite, project identity, the existing task machinery, and the normal CLI. The per-project broker owns canonical message, participating-session, attempt, and receipt state and invokes the native driver modules itself. The machine runtime and its database are removed from message delivery. Agent shell commands and enrollment hooks use broker RPC and never open canonical databases. Provider runtimes remain independently owned processes; a broker restart does not terminate them.

Provider mechanics belong under an internal driver package; they must not be embedded in broker routing. The broker schedules transport attempts and enforces generic state transitions; agents still own the meaning of messages and work. All paths, limits, timeouts, binaries, and provider defaults resolve through `internal/config/`.

A minimal driver boundary supports probe/attach, readiness observations, submit, reconcile, and close. Submission observations distinguish definite non-submission, retained input with evidence (accepted or held), refusal, and uncertain possession. Unsupported/disconnected are availability facts; disconnection after intent cannot imply non-submission. Drivers contain protocol translation and connection state only, with no durable queues, alternate routes, or independent retry policies. Native per-message withdrawal is explicitly unsupported in the initial contract. The interface is internal until both implementations prove it.

All startup hooks perform bounded registration or report unavailability and continue. `--help` must not instantiate a client, probe a provider, start a broker, require Git, or touch state. Normal commands fail with contextual errors. A receiver that lacks a documented capability is visibly unsupported rather than silently routed through terminal text or hooks.

## Exclusive broker ownership

The canonical database contains one broker ownership row: a random owner instance ID, monotonically increasing generation, and non-reused OS process identity (boot identity, PID and process-start identity). The broker's ownership component alone acquires/releases this row. Acquisition uses a short SQLite write transaction that validates the prior tuple and increments its generation atomically. It does not hold a database transaction open for the process lifetime. Generation overflow, malformed ownership, or unavailable process identity fails closed.

This is a process-lifetime exclusive lease with no timeout-based revocation. A second broker may acquire only after an explicit orderly release or positive OS evidence that the recorded process incarnation has exited. Missing PID files, slow health responses, silence, and denied process inspection do not establish exit. Reclamation compares and updates the unchanged ownership tuple transactionally after checking process identity. An alive, suspended, or hung owner blocks replacement; startup returns an ownership error within the configured command deadline. We deliberately do not use expiring heartbeats: database fencing alone cannot prevent a paused, replaced broker from later submitting native input or unlinking a socket.

Every canonical mutation, including tasks, session registration, queue selection/intent creation, receipts, budgets, migration activation, and ownership release, checks the same owner/generation inside its write transaction. Store APIs require that ownership context; CLI and maintenance code cannot bypass it with independent database writes. Queue selection and intent creation are one transaction. A stale handle with an old generation must fail even if its database connection remains open. Offline schema conversion acquires the same exclusive ownership under the cutover procedure; it is not an online second writer.

The broker also owns an in-process admission boundary for work that can submit native input, write state, or clean up endpoints. Shutdown closes admission and joins all admitted work. It closes drivers/listener, drains callbacks, and completes socket/PID cleanup while still owning the row; it releases ownership last. No deferred cleanup is allowed after release. If an operation cannot be joined, shutdown reports failure and retains ownership; replacement requires verified process exit. A result can outlive the provider connection, so closing a socket alone is not a drain proof. Already-retained provider work is governed by the message lifecycle, independently of broker exit.

Only the acquired owner creates/removes its protocol-version socket and PID file. All starts share this ownership path. Remove CLI health/PID-based replacement, handshake-timeout cleanup, unconditional constructor cleanup, and unconditional post-release shutdown cleanup. PID and health become diagnostics. Hooks and ordinary CLI calls never start a broker; a missing service is an explicit prerequisite failure. Start the broker independently of enrolled provider process trees, through the user's service lifecycle or an independent terminal, so Claude cannot classify the broker as its own child. If that separation cannot be established for an enrollment, reject it rather than launching a helper to impersonate a peer.

## Session identity and trust

Canonical identity records include a globally unique session incarnation, project, provider/runtime type, provider conversation ID, user-facing name, broker ownership generation, opaque endpoint binding, capabilities, readiness, and activity times. This replaces name/PPID/TTY watches as the routing source; it is not an additional registry beside them. PID and process-start observations are supplemental diagnostics, not routing keys.

Registration binds the concrete runtime endpoint and returns a broker-issued per-incarnation scoped credential over a private local channel. Sender identity comes from that authenticated registration; `--name` selects a label and cannot impersonate a registered sender. Agent-facing connections use the broker's private local socket with explicit role and scope checks. Provider account authentication stays inside the provider installation. Claude's messaging token is never transmitted to, stored by, or used by the broker or its driver. Waggle outbound credentials are independent random capabilities; there is no need to reuse or derive them from a native messaging token.

Enrollment has explicit pending, bound, disconnected and retired states. Pending enrollment cannot send, receive, or report readiness. The supported host hook must supply the native conversation ID and exact endpoint, and ordinary tool calls must demonstrate the matching outbound credential before activation. Endpoint ownership and session binding must be verified, not inferred from an arbitrary path or label. Two sessions sharing a directory must not share credentials. This isolates legitimate registered sessions; a fully privileged malicious same-OS-user process is not contained by Unix socket permissions alone.

Claude enrollment passes only the native socket endpoint, provider session identity and Waggle registration material, never `CLAUDE_CODE_MESSAGING_TOKEN`. Its documented SessionStart-to-Bash environment facility carries the independent Waggle credential. Codex uses per-thread launched-session configuration for ordinary shell tool calls on the explicitly attached TUI. The configuration fields and SessionStart identity are inputs to an M1 proof, not proof of end-to-end propagation: process-wide server environment, undocumented hook exports, transcript inspection and PID inference cannot substitute. If the selected per-thread mechanism fails, declare Codex outbound unsupported and stop M1. Do not add another tool transport to obtain success.

After a broker restart, persisted sessions begin disconnected/unverified. Only native reconnection to the same explicitly bound endpoint and provider conversation plus observed readiness makes them ready. Broker ownership generations fence stale callbacks. Known provider conversation IDs remain available for reconciliation. Closing a terminal view is distinguished from terminating the provider runtime; no claim is made to restore private in-memory process state after a machine crash.

## Message and attempt lifecycle

Extend message storage with canonical sender/recipient session references, conversation ID, reply-to message ID, deadline, deduplication key, and provenance. Existing numeric IDs can remain internal database keys; externally exchanged message/session identifiers must be globally unique. Message text stays untrusted text, with bounded size and explicit peer provenance.

Each dispatch has one immutable attempt ID, owner/generation, submission intent, and provider reference when observed. Selection and intent commit reserve the recipient barrier before any provider call. The broker applies evidence only to the original attempt and recipient incarnation under current broker ownership. No second attempt is created for a message in the initial contract. Definite non-acceptance is a visible failure; loss after intent is uncertain, even if no actual write is known. Restart schedules only stored work without intent. Reconnection and client message IDs never justify resubmission.

One broker transition function derives scheduling eligibility and user-visible status from durable intent, observed receipt evidence, and the message/conversation stop or deadline disposition. These are different facts, not competing success flags. Inbox and event views are read-only. Transport bytes written, a successful socket close, or provider turn completion without message correlation are not receipts.

Ordering is per recipient incarnation in queue sequence order: at most one Waggle message may be awaiting proof of consumption or non-retention. It is an input-consumption guarantee, not completion ordering for arbitrary tools or human work inside the provider. The barrier has these rules:

- Before intent, a stored message has not left Waggle. Cancellation or expiry prevents intent atomically; removing it from eligibility does not block subsequent eligible messages.
- Intent committed, submission in progress, or unknown result retains the barrier. The provider may already possess input. Process interruption does not release it.
- Native accepted or held evidence retains the barrier. Both mean the provider can still consume the input later. A held outcome is conclusive about retention, not completion.
- Correlated acknowledgement/reply from the exact receiving session proves consumption and releases the barrier. This does not prove that resulting native work has finished. Alternatively, provider evidence specific to this attempt proving refusal, drop, or absence of retained input releases it. A transport rejection proves non-retention only when M1 establishes that meaning.
- Deadline, stop request, native disconnection, and elapsed time cannot release a barrier after intent. Later messages to that incarnation remain visibly blocked by the original message ID. Queue bounds still apply.

Cancellation and deadline behavior are deliberately limited to guarantees the broker controls:

- Before intent, cancellation is confirmed locally and expiry is final for dispatch. A concurrent scheduler must serialize with that transition so only one wins.
- After intent, persist cancellation requested or deadline elapsed and stop all future dispatches in that Waggle conversation, including queued replies. Withdrawal remains unsupported in the initial native contract; if the original submission result is also unknown, report both unsupported withdrawal and uncertain possession. Never label this simply cancelled or safely expired.
- While a provider holds input, approval or a provider settings change may deliver it after Waggle stops. Waggle performs no mode change, automatic resend, or replacement delivery. Retention and its barrier remain until correlated consumption or definitive drop evidence arrives.
- After consumption/acceptance, stopping Waggle stops future Waggle dispatches, not native execution, tools, or effects already initiated. The broker invokes neither Claude session termination nor Codex `turn/interrupt`. Codex exposes turn-level interruption, which cannot establish per-message withdrawal from a turn shared with human input. Native stop remains under the human's ordinary provider controls; any resulting observations must be reconciled for this message before changing retention state.
- Late receipts append evidence to the same attempt and can establish consumption or drop. They never erase the stop/deadline disposition, restart the conversation, reset its budgets, or authorize a resubmission. A late reply is inspectable but does not automatically trigger another reply.

Operator resolution is explicit: request reconciliation using provider evidence, or retire the blocked Waggle recipient incarnation and cancel its unsent queue. Retirement disables its routing permanently and reports that previously submitted native work may remain. It does not clear uncertainty or cancel that work. Re-enrolling the same provider conversation cannot bypass an unresolved barrier; require evidence of consumption/drop or conformance-proven absence of retained input across termination and resume before rebinding it. Process exit alone does not prove that a durable provider queue is empty. A genuinely new provider conversation gets a new incarnation without transferring the old queue. There is no force-clear-and-continue action. Without evidence or retirement, the barrier can persist indefinitely; the UI reports the required intervention rather than declaring timeout success.

Sending an agent message never approves the recipient's tools or changes its model/sandbox/approval settings. Peer provenance is explicit, and peer-supplied fields cannot become provider permission controls. Conversation deadlines and turn/hop budgets are inherited and decremented by canonical operations. Stop/deadline and exhausted budgets reject new dispatches even if an agent replies late or tries to create a reply with reset metadata. These limits bound Waggle dispatches; they cannot bound arbitrary native execution after delivery.

## Ordered delivery and persistence migration

Use one broker-owned durable ordered queue. A message commit assigns a per-recipient sequence and wakes the broker scheduler; that scheduler selects eligible rows from canonical SQLite and invokes the recipient's native driver. Startup drains the same queue through the same scheduler. An in-memory wakeup is only a scheduling hint, never a delivery record. There is no separate catch-up handler, live push dispatcher, delivery subscription, or second transport cursor. The old replay/live race is eliminated by removing that handoff from the production path. Read-only event subscriptions may display state but cannot dispatch or acknowledge messages.

Queue scans are bounded, ordered, and use the ownership and retained-input barrier defined above. Message identity deduplication and capacity validation live in the broker. Capacity pressure returns explicit backpressure; no message is silently dropped and no alternate transport is started. Fault tests must prove that interruption between commit, wakeup, selection/intent, native submission, and receipt cannot strand eligible stored work or repeat retained/uncertain input.

Cutover is machine-wide because the old runtime database spans projects. Inventory every known project store, runtime writer, broker, installed Waggle hook, and launch/install entrypoint. Require verified cessation of every old writer before taking consistent SQLite snapshots, including committed WAL contents. A schema change does not fence old connections already open. If process cessation or the source inventory cannot be established, fail before mutation. Preserve original snapshots and task data; never replace a live database inode underneath open writers.

Keep one canonical database at the exact existing `config.NewPaths(projectID).DB`: currently `~/.waggle/data/<hash>/state.db`. Preserve the existing project-ID-to-hash mapping. Update the existing shared `schema_version` table from exactly one row with version 1 to exactly one row with version 2 in the conversion transaction; reject missing, duplicate or inconsistent version rows. `internal/tasks/store.go:110-116` is the previous broker's actual rejection point. New tasks/messages share one schema validator and ownership context. There is no second operational database at a different path.

Only IPC identities change with the incompatible protocol: under the same resolved data and socket directories, use `waggle-v2.pid` and `broker-v2.sock`. The legacy names are `waggle.pid` and `broker.sock`. Define these defaults and protocol/schema versions only in `internal/config/`; never discover or fall back to the other version's endpoint. After verified shutdown, retire old socket/PID files without redirects or a legacy listener. This isolates the native endpoint from the old CLI's timeout cleanup even when the new broker is suspended. Keeping the same socket and merely answering errors cannot provide that guarantee during a timeout.

The native endpoint uses one bounded newline-JSON decoder with an explicit required protocol version. Missing or unsupported versions receive a complete newline-terminated unsupported-version error, before command execution, for all commands including status, connect, replay, ack and push.reserve. This is input rejection in the canonical decoder, not legacy request translation. If the broker is unresponsive, no response-time guarantee is claimed; version-separated IPC provides isolation. Actual old-binary tests must assert native socket/PID continuity and unchanged canonical data after foreground start, auto-start, health and handshake timeout cleanup, replay, ack and reservation attempts. A custom caller forcibly pointed at native IPC is distinct from the old binary's default path behavior.

Partition runtime records by their exact stored `project_id`, then validate the established hash mapping against the inventory; a truncated directory hash is not an identity. Import matches into the corresponding target in a single transaction per project, preserving source identity and treating every historical delivery as unconfirmed. Preserve unmatched/ambiguous records in the source snapshot with an explicit unassigned report, never guess a target. Conversion leaves each project unactivated. Verify all conversions before activation/start of any native broker. Per-project activation is explicit and resumable; there is no claimed transaction spanning all databases. Interruption during conversion leaves enrollment disabled; interruption during activation leaves remaining projects unstarted, with no old runtime bridge. No historical message is automatically submitted and all sessions enroll afresh.

The retired machine runtime has no version fence (`internal/runtime/store.go:64`), and an old normal start auto-installs adapters before checking the broker (`cmd/start.go:75`). Therefore cutover must retire discovered old launch/install paths as well as writers. Arbitrary later execution of an old installer under the same OS user can recreate legacy state or hooks; Waggle cannot prevent that with a database version or lease. Such reinstallation is outside the supported cutover state, never a migration fallback. Tests of those old entrypoints use isolated configuration roots and report side effects while proving they cannot change native canonical receipts. If preventing arbitrary old installation is required, external execution/configuration controls are a prerequisite; no local guarantee is claimed here.

Required removal within messaging scope: broker name-push fallback and listener-derived presence; runtime watch/record/signal delivery and notification retry loops; PPID/TTY routing files; signal-consuming shell/PreToolUse hooks; bootstrap and runtime-pull receipt mutations; inbox mark-seen mutations; separate catch-up/listen delivery; CLI access to runtime storage; and the startup/recovery/cleanup paths superseded by broker ownership. Keep bounded enrollment hooks only. Installer retirement touches only known Waggle-owned blocks/files and preserves unrelated settings. Other providers explicitly report unsupported native receive capability, with no legacy delivery route.

## Provider-specific implementation

Codex: initial verified installation is CLI 0.153.4. The user/service lifecycle owns that server process; the broker attaches and never creates a replacement server, forks a transcript, or kills it on broker shutdown. Each TUI conversation is separately enrolled by exact thread ID. Broker restart reconnects only to that registered endpoint. The claim that plain `codex` automatically uses the shared daemon remains unconfirmed and is unnecessary to this supported topology.

Use the pinned server's native Unix transport: the current App Server reference specifies WebSocket framing over AF_UNIX with HTTP Upgrade.
