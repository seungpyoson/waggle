# Native messaging implementation plan

Status: revision 6, design revision dated 2026-09-07 responding to the supplied revision 5 reviews. This revision separates orderly draining from interruption, fixes persisted endpoint authority, and replaces an unspecified reconciliation promise with named evidence rules and an explicit availability limit. These are proposed replacement behaviors, not claims about the current implementation or approval of the revised acceptance contract. Production implementation remains paused; native conformance is not confirmed.

The user authorized implementation of reliable Codex↔Claude and Codex↔Codex communication, with approval from Claude Fable 5.1 at xhigh and Codex GPT-6 Astra at xhigh at key milestones. The original assessment was completed against `5fac0530a789f54b2a87fb10d9d21a14b2dded91`. This plan implements that objective; a successful model invocation or cooperative inbox pull is not completion.

Related work: GitHub issues #132 (liveness), #136 (ordered replay), #137 (bounded catch-up), #138 (receipt handoff), #139 (direct target validity), #140 (real-session evidence), #141 (diagnostics), #143 (sender identity); roadmap #142. ## Acceptance contract

The release must demonstrate, on this user's local subscription-authenticated runtimes:

1. Claude→Codex→Claude, Codex→Claude→Codex, and Codex A→Codex B→Codex A, with distinct concrete conversations and replies correlated to the original message.
2. Idle recipients whose native inbound policy permits delivery start processing without another human prompt, shell command, or manual inbox poll, including freshly enrolled sessions with no prior ordinary tool call. Native hold/refuse policy remains effective. Busy recipients safely receive later or produce an explicit held/refused result.
3. Participating agents retain normal interactive use. The supported Codex entrypoint is its normal TUI explicitly attached with `--remote unix://<registered endpoint>` to a user-owned App Server. Plain `codex` sessions are not assumed to use that endpoint. Starting a different worker must never be reported as reaching an existing session.
4. Names resolve unambiguously to an exact session incarnation. Two Codex sessions in the same directory cannot share identity. Known history, a live Waggle listener, a PID, or a transcript is insufficient to report runtime readiness.
5. Unknown/dead direct targets fail explicitly. Persisting a message is reported as stored, never runtime-accepted or replied. Offline durable enqueue is an explicitly different operation; it is not silently substituted for direct delivery.
6. Restart before dispatch preserves pending work. Ambiguous acceptance is reconciled from provider evidence or remains explicitly uncertain. No blind retry can duplicate a possibly accepted write-capable request. Stale workers cannot commit receipts for a newer attempt.
7. One bounded ordered queue, explicit backpressure, inherited conversation budgets, and deadlines/stop enforced at Waggle's dispatch boundary. Once a provider may possess input, Waggle cannot promise withdrawal or cessation of native work. Retained input keeps its ordering barrier until evidence resolves it; expiry alone cannot release it. The lifecycle below defines these limits before implementation.
8. Peer messages confer no permission. Runtime policies and inbound controls remain effective, sender identity is derived from a scoped registration, and tokens/credentials are never printed or placed in prompts. No paid API fallback or account rotation is introduced.
9. Build, applicable tests, degraded-state CLI help, native conformance, real-session matrix, and both final reviews pass. Missing environment evidence is not a pass. No merge or deployment is implied by reviewer approval.
10. Closing an interactive view while its native thread remains loaded must preserve that thread's private receipt authority; M1 must prove this for each supported topology. If the native credential scope is actually lost and no attempt-specific provider evidence exists, the original conversation can remain permanently blocked, including after retirement or restart. There is no administrative force-clear or claimed recovery from missing evidence. This explicit availability limit is a revision 6 acceptance decision for review; rejecting it requires a supported durable evidence/recovery contract before implementation, not a guessed receipt.

The broad execution platform (objectives, work graphs beyond existing tasks, evidence marketplaces, fleet reconstruction, ACP/A2A federation, topology selection) remains future work. Stable identities, durable attempts, and explicit driver capabilities are founding boundaries now.

## Invariant, responsible component, and production evidence

Invariant: a durable message is addressed to one exact runtime incarnation and remains in an explicit state supported by observed native acceptance or a correlated reply. Storage, notification, transport progress, and model response are different facts. Only the per-project broker may transition canonical message/session/attempt state.

At the base commit, the production path was CLI `send` → broker `handleSend` → name/name-push socket → runtime `handleDelivery` → a second SQLite record → `notifyRecord` → signal file → shell/PreToolUse hook. Bootstrap independently opened the runtime store and marked records surfaced/dismissed before its caller printed them. That broker never observed native input acceptance. This paragraph describes the base commit, not the subsequently modified working tree.

Direct evidence at the base head: `internal/broker/router.go:668` stores before target resolution; `internal/runtime/manager.go:382` writes the second record; `manager.go:483` writes the signal and marks notification; `internal/adapter/bootstrap.go:121` dismisses before returning; `cmd/adapter.go:53` calls Bootstrap before rendering; `cmd/runtime_pull.go:37` marks surfaced before printing. A prior local fixture executed the shipped Claude push hook and observed exit 0, a deleted signal, and top-level `additionalContext`. The current hooks reference does not add that top-level field to context for PreToolUse. The failure is the unsupported field at the installed event and consumption before host evidence; changing the envelope would not establish reliable receipt or idle delivery. The fixture is reported prior local evidence, not live-provider E2E evidence.

Additional confirmed ownership failures: `cmd/start.go:44` enters foreground construction without an ownership check; `internal/broker/broker.go:113,329` unconditionally removes the socket; `cmd/root.go:47-64,136-169` removes socket/PID after health or handshake timeouts. A process may still be alive with a database handle. `internal/messages/store.go:279-301` also mutates receipt-like state when inbox is read. These writers and destructive recovery paths cannot enforce a sole-owner invariant.

The base design could not enforce the invariant because none of its canonical-state writers owned the native input boundary, and they independently interpreted receipt. The working tree has since centralized canonical writes in `brokerstate` and removed substantial legacy delivery code. Its remaining defects concern provider composition, resource lifetime, shutdown supervision, global scheduling dependencies, bootstrap handoff, and error-driven project identity selection. This design retains the fenced transaction implementation and replaces those boundaries.

## Architecture and authority

Keep Go, SQLite, project identity, the existing task machinery, and the normal CLI. The per-project broker owns canonical message, participating-session, attempt, and receipt state and invokes the native driver modules itself. The machine runtime and its database are removed from message delivery. Agent shell commands and enrollment hooks use broker RPC and never open canonical databases. Provider runtimes remain independently owned processes; a broker restart does not terminate them.

Provider mechanics belong under `internal/broker/enrollment/internal/native`. The `internal/broker/enrollment` package implements workers and exposes only their owner-mediated start entrypoint; it never returns a callable transport or `ManagedWork` value. Go's internal-package boundary prevents broker RPC handlers, CLI, config, protocol, and domain packages from importing raw native mechanics. The broker schedules transport attempts and enforces generic state transitions; agents still own the meaning of messages and work. All paths, limits, timeouts, binaries, and provider defaults resolve through `internal/config/`.

A minimal private driver boundary supports attach, readiness observations, submit, correlated evidence, and interruption/join. An enrollment worker alone owns the target and callable transport; general callers do not receive provider handles. Submission observations distinguish definite non-submission, retained input with evidence (accepted or held), refusal, and uncertain possession. Unsupported/disconnected are availability facts; disconnection after intent cannot imply non-submission. Drivers contain protocol translation and connection state only, with no durable queues, alternate routes, or independent retry policies. Native per-message withdrawal is explicitly unsupported in the initial contract.

The authority assignment is:

- `brokerstate.Owner`: database acquisition, operation admission, managed-work accounting, endpoint publication, shutdown supervision, and release.
- `messages`: enrollment and reservation transitions, readiness evidence, authorization scope, queue eligibility, budgets, attempts, barriers, and receipts in fenced transactions.
- Broker enrollment worker: the physical transport and every constructor, request, reader, callback, and teardown associated with one reserved enrollment. Its in-memory state cannot establish canonical readiness or receipt.
- `config`: one closed provider-contract catalog, selected project identity, and operational bounds. A catalog entry identifies a complete versioned integration, including hook assets, bootstrap mechanism, topology, and native protocol. Consumers dispatch by that contract; they do not maintain separate supported-provider lists or partial capability switches. Build-time coverage tests enumerate every catalog entry against installer, enrollment parser, and private driver implementations. Passing those tests does not establish native conformance.
- `protocol` and broker ingress: bounded wire decoding and verified connection principal. Domain transactions enforce command-specific credential scope.
- Command supervisor: immediate reporting of service failure and shutdown deadlines while the owner continues tracking unfinished work.

One complete provider is proved first, then the other through this same structure. The release still requires both providers and all conversation directions. Until conformance establishes a complete entry, configuration cannot make an incomplete integration appear supported. Persisting an endpoint records an authorized binding; it does not authorize an arbitrary endpoint supplied by an RPC caller.

Persisted endpoint bindings are authoritative. The catalog fixes a provider's topology and protocol, not a competing runtime endpoint. For the shared Codex App Server, canonical `provider_bindings` records have immutable IDs and endpoints, with one current binding per project/provider. Enrollments reference a specific binding ID; replacement cannot retarget an existing enrollment. Bootstrap must match the selected stored binding rather than authorizing its own App Server.

The retained `start --codex-app-server <endpoint>` option has exactly one meaning: under the verified local operator principal and acquired owner, register the initial binding if none exists; otherwise assert equality with the stored endpoint. Omission uses the current stored binding. A mismatch returns a contextual error before workers or native connections start and never overwrites the row. Config validates the endpoint's supported representation before this transaction; it does not probe alternatives. With no stored endpoint and no supplied value, the broker may serve tasks and diagnostics, but Codex enrollment reports the missing binding.

Replacement uses an explicit operator RPC/CLI, `waggle provider endpoint replace codex <endpoint> --expected-binding <id>`. It compares the current binding ID in the fenced transaction, requires every enrollment referencing it to be retired and every associated reservation to have been released after join, then creates a new immutable binding and makes it current atomically. It does not implicitly retire sessions or close resources. Concurrent replacement or registration either serializes or fails its expected-binding check; failure changes nothing. Historical bindings, attempts, and barriers remain, and same-conversation checks span all binding IDs. An unreachable replacement does not reactivate the old endpoint. This command uses the ordinary broker RPC ownership path, with no offline second writer. Start the broker without an endpoint override to administer an existing unavailable binding.

Claude's catalog entry instead defines a per-session native endpoint supplied by the verified bootstrap principal. Preparation persists that exact immutable endpoint with the incarnation; there is no shared Codex-style endpoint flag for Claude. In both topologies workers use the stored enrollment binding exclusively. Provider-specific endpoint shape is a contract distinction, not an alternate authority.

All startup hooks perform bounded registration or report unavailability and continue. `--help` must not instantiate a client, probe a provider, start a broker, require Git, or touch state. Normal commands fail with contextual errors. A receiver that lacks a documented capability is visibly unsupported rather than silently routed through terminal text or hooks.

## Exclusive broker ownership

The canonical database contains one broker ownership row: a random owner instance ID, monotonically increasing generation, and non-reused OS process identity (boot identity, PID and process-start identity). The broker's ownership component alone acquires/releases this row. Acquisition uses a short SQLite write transaction that validates the prior tuple and increments its generation atomically. It does not hold a database transaction open for the process lifetime. Generation overflow, malformed ownership, or unavailable process identity fails closed.

This is a process-lifetime exclusive lease with no timeout-based revocation. A second broker may acquire only after an explicit orderly release or positive OS evidence that the recorded process incarnation has exited. Missing PID files, slow health responses, silence, and denied process inspection do not establish exit. Reclamation compares and updates the unchanged ownership tuple transactionally after checking process identity. An alive, suspended, or hung owner blocks replacement; startup returns an ownership error within the configured command deadline. We deliberately do not use expiring heartbeats: database fencing alone cannot prevent a paused, replaced broker from later submitting native input or unlinking a socket.

Every canonical mutation, including tasks, session registration, queue selection/intent creation, receipts, budgets, migration activation, and ownership release, checks the same owner/generation inside its write transaction. Store APIs require that ownership context; CLI and maintenance code cannot bypass it with independent database writes. Queue selection and intent creation are one transaction. A stale handle with an old generation must fail even if its database connection remains open. Offline schema conversion acquires the same exclusive ownership under the cutover procedure; it is not an online second writer.

The broker also owns an in-process admission boundary for work that can submit native input, write state, or clean up endpoints. Shutdown closes normal admission and starts draining. A shutdown-join deadline configured in `internal/config/` bounds each caller's wait and the command's failure report; it does not terminate the finalizer. An unresponsive close must not prevent reporting that deadline. On timeout admission remains closed and ownership remains retained. The same finalizer may later complete cleanup and release after actual quiescence. It never reopens service. Closing a socket alone is not a drain proof. Already-retained provider work is governed by the message lifecycle, independently of broker exit.

Only the acquired owner creates/removes its protocol-version socket and PID file. After proving the recorded predecessor exited and acquiring the next generation, it may remove that predecessor's leftover v2 endpoint files at the configured paths before binding its own; validate expected ownership/type and reject symlinks or inconsistent files. No non-owner cleanup is permitted. All starts share this ownership path. Remove CLI health/PID-based replacement, handshake-timeout cleanup, unconditional constructor cleanup, and unconditional post-release shutdown cleanup. PID and health become diagnostics. Hooks and ordinary CLI calls never start a broker; a missing service is an explicit prerequisite failure. Start the broker independently of enrolled provider process trees, through the user's service lifecycle or an independent terminal, so Claude cannot classify the broker as its own child. If that separation cannot be established for an enrollment, reject it rather than launching a helper to impersonate a peer.

## Managed workers, operation admission, and finalization

Use two distinct lifetimes: a registered worker owns physical resources; a scoped operation admits a particular workflow. The owner accounts for both. A worker is not a long-lived `Operation`, and resources are never members of `operationState.resources`.

The proposed Go surface below is a contract sketch, not implemented API. Existing scoped read/write transaction methods remain. The owner invokes completion through its private transaction path; there is no public operation that bypasses admission during draining.

```go
type WorkLifetime struct {
    Stop <-chan struct{}       // Orderly drain: start no new workflows.
    Interrupt context.Context  // Cancel native I/O on fatal failure or escalation.
}

type ManagedWork struct {
    // Passive until called by StartWork. Returns only after physical resources
    // are closed and every owned constructor, request, reader and callback joins.
    // Report a fatal failure before entering cleanup that may block.
    Run func(lifetime WorkLifetime, reportFatal func(error))

    // Registered together with Run. Invoked by the owner after Run joins,
    // including during draining. SQL-only completion of this work's accounting.
    Complete func(tx *WriteTx) error
}

func (o *Owner) StartWork(ctx context.Context, key string, work ManagedWork) error
func (o *Owner) Do(ctx context.Context, work func(*Operation) error) error
func (op *Operation) Write(ctx context.Context, change func(*WriteTx) error) error
func (o *Owner) BeginShutdown(cause error)
func (o *Owner) Interrupt(cause error)
func (o *Owner) Wait(ctx context.Context) error
```

`StartWork` inserts a unique key and schedules its passive `Run` in one synchronized decision against draining. Duplicate registration never creates another worker. The enrollment package constructs these callbacks privately and passes them directly to the owner; it does not publish a `Run` function for handlers to invoke without registration. `Complete` is mandatory for an enrollment worker. Ingress and endpoint constructors remain owner-internal tracked work, without dummy empty completion transactions. The request context bounds admission only. Accepted workers receive two owner signals: `BeginShutdown` closes `Stop` and normal admission together; it does not cancel `Interrupt`. Registry locks protect insertion, publication, and completion bookkeeping only. They never span SQL, provider construction, provider calls, or joins. Broadcasting either signal cannot wait for an arbitrary provider closer.

Every constructor, readiness workflow, and dispatch starts through normal `Owner.Do`. A dispatch's admission lasts through selection/intent, its single native call, and result persistence. Its native-call context derives from `Interrupt` and the configured request deadline, never from `Stop`, the originating command context, or a shutdown waiter's deadline. An orderly drain lets an admitted call finish within its own bound. Expiry of that call's deadline can still produce uncertainty. Cancellation of native I/O does not cancel the separately bounded final result transaction. `Operation.Write` remains usable by that already-admitted callback during draining; it expires only after the callback and work it started have joined. A new `Do` after draining fails. There is no empty transaction immediately before a provider call, and no resource-owning operation authorizing another operation's effects.

On `Stop`, a worker with an admitted workflow completes that workflow and its result persistence before closing the transport. A worker without one starts closure immediately. Each worker makes this decision independently. Closure interrupts permanent readers and then joins them; it must not wait for reader exit before initiating the close that permits exit. `Interrupt` first begins draining, then cancels active native calls without waiting for their mutexes. Fatal worker/domain failure invokes it before cleanup. The first SIGINT/SIGTERM or ordinary broker-stop request initiates orderly draining; a subsequent operator OS signal while draining escalates. The command keeps observing those signals after ingress closes; escalation does not require a new RPC through closed admission. Duplicate ordinary stop RPCs, when still accepted, remain idempotent. A reporting deadline never escalates automatically. Transport interruption neither invokes provider turn cancellation nor proves non-retention.

Worker completion is the other explicitly admitted obligation. Its SQL-only `Complete` callback is fixed at registration, runs after physical teardown joins, and remains counted until its fenced transaction commits. It can clear this incarnation's readiness and release its terminal reservation. It cannot construct a provider, select a message, submit input, or accept new requests. In particular, it does not try to acquire a new `Do` after admission has closed. There is one canonical SQL implementation of these transitions in `messages`; the owner supplies a scoped `WriteTx`, never a raw database or unfenced executor.

A transport constructor records each connection and reader in its worker before proceeding to another fallible initialization step. Failure uses the same interruption-and-join routine as successful construction. The interrupt observer can interrupt transport I/O without waiting for the active request's mutex; the worker joins that observer too. An admitted constructor finishing during orderly drain cannot publish a usable transport; its created resources still count until closure joins. At most one physical transport generation belongs to an enrollment worker at a time. A replacement connection to the same recorded endpoint can open only after the previous transport joins.

`Run` returning is a concrete implementation contract, not a compiler proof that arbitrary goroutines joined. An unresolved close error is reported through `reportFatal` while the worker remains registered; it cannot return and claim quiescence merely because it logged the error. A failed completion transaction likewise retains the registry entry, reports failure, and prevents orderly ownership release. Reporting a deadline never causes either condition to be treated as success. SQLite uses its configured contention bound within the transaction attempt; after that attempt returns failure there is no automatic replay of the domain callback. This deliberately includes a transient failure that has already exhausted that bound: it prevents orderly release and requires operator recovery through process exit and fenced reacquisition. A later `Wait` cannot retry the callback or call the failure quiescence. Tests must distinguish this failure from a waiter timeout followed by successful completion.

Native events are consumed within the worker's joined reader lifetime. Any provider-specific evidence handler is typed to observations for the exact existing attempt and incarnation and has no submission authority. Event arrival is not admission: it must win `Owner.Do` before normal admission closes. If admission wins, its fenced persistence finishes before reader join. If draining wins, it performs no mutation, reports no recorded receipt, and leaves the barrier intact while joining normally. A response belonging to an already-admitted dispatch is persisted within that dispatch and needs no new admission. Events from a closed reader or another generation cannot reactivate enrollment or mutate a successor. Do not introduce a general draining-time SQL capability to admit a new event.

Owner progress is `serving → draining → quiescent → endpoints cleaned → released`. Deadline reports do not change progress. Fatal scheduler or canonical-persistence failure invokes `Interrupt` before blocked cleanup, closing admission synchronously and signaling every worker. The command observes failures and the reporting deadline concurrently with service completion; it does not wait for `Serve` first. After reporting timeout, the foreground process remains draining. Its eventual exit is nonzero even if cleanup subsequently succeeds, and the final diagnostic reports both the missed deadline and actual release. A later independent `Wait` can return success after release: the command's failed deadline is not a permanent owner-finalization error. Forced process termination is separate from orderly shutdown and cannot be described as a joined release.

`Bind` reserves a tracked endpoint constructor before filesystem work. Final publication and the transition to draining use the same lifecycle synchronization. If draining wins, the constructor closes its result and completes tracked cleanup without making ingress usable. Do not hold the lifecycle mutex across bind, unlink, filesystem queries, or listener close; otherwise those calls could prevent `BeginShutdown` and its error report. Owner release waits for any unpublished constructor too.

After all operations, workers and completion transactions finish, the owner validates its fence, removes only recorded endpoint identities, and releases the row last. Successful removal of each file is recorded in the owning endpoint's in-process cleanup progress. SQLite rollback cannot undo unlink. A later cleanup failure therefore retains ownership without forgetting which removals succeeded; a changed or unattributed pathname is never accepted as successful cleanup. After a crash, the successor follows predecessor-exit reclamation, accepting genuinely absent files and validating remaining files. No former-owner cleanup callback can remain after release.

## Reservation and scheduling contract

Create one `enrollment_slots(enrollment_id PRIMARY KEY REFERENCES enrollments(id))` reservation in the same fenced transaction as enrollment preparation. Capacity counts these reservations, including preparations and terminal enrollments with unfinished teardown. No second live-enrollment count or handle-map size independently admits another resource. Lowering configured capacity below outstanding reservations fails explicitly.

A bounded database scanner registers one worker per reserved enrollment, including terminal rows awaiting cleanup. Workers have no message mailbox, retry queue, readiness flag, or receipt ledger. Wakeups carry no work; periodic database discovery handles lost wakeups. A worker loads its immutable binding and verifies the reservation before any provider access. A stale scan started after slot deletion therefore cannot create a transport.

Each worker independently observes its own target and selects at most one eligible message for that recipient. Selection rechecks enrollment, its existing reservation, current ownership/readiness evidence, message deadline, stop, shared hop budget, and absence of an attempt/barrier in the intent transaction. Queue capacity is checked when accepting a new enqueue, not when dispatching an already-stored message: a full queue must still drain. Conversation budget expenditure is shared across workers and commits atomically with intent; with one remaining hop, exactly one competing recipient may commit and submit. The worker uses its own current transport through submission and result persistence. There is no lookup of another worker's handle after intent commit and no durable `attached` flag. Readiness remains observed canonical evidence and is cleared on broker restart; it is not a guarantee that the next provider call succeeds.

Config owns positive bounds for reservation-discovery interval/page size, each worker's minimum queue-check interval, readiness-probe interval, and reconnect backoff. Wakeups coalesce and cannot bypass the minimum queue-check interval; lost wakeups are covered by periodic checks. Idle work performs bounded reads and writes only changed canonical observations, not an empty fencing transaction or a heartbeat write on every scan. A read indicating possible queued work is only a hint to enter the intent transaction; that transaction remains the sole eligibility decision and rechecks all constraints. With C reserved workers, idle queue-check rate is bounded by C divided by the configured minimum interval, plus the separately bounded reservation scanner and readiness observations. This scheduling cadence is execution bookkeeping, not cached eligibility or a second queue. Load verification must measure the configured bound at full reservation capacity and assert no wakeup-driven busy loop or starvation.

When a transport becomes unavailable, the worker records disconnection, closes and joins that transport, and may reconnect to the same binding under configured observation/backoff bounds. This never reselects a message with intent. A blocked constructor, probe, or closer delays only its enrollment. Shared native-server outages can affect multiple workers; there is no claim of independence from the provider itself. No global reap or observation barrier precedes dispatch to another already-bound recipient.

Retirement or enrollment expiry disables routing transactionally but retains the reservation. Retirement stops new workflows; an already-admitted submission and its result persist under the same orderly-drain rule before transport closure. Expired preparing/pending enrollments cannot have admitted a submission. After transport closure joins, the registered completion transaction deletes the reservation only if the enrollment is terminal. A live worker stopped by broker shutdown keeps its reservation for restart and loses current readiness. The worker stays registered until this completion commits; scanning cannot start another worker in the gap between join and slot release. An explicit owner interruption can cancel active I/O, but still cannot clear its barrier.

On broker restart, persisted reservations are reconciled under the newly acquired generation before native access. Live enrollments keep their slots and undergo readiness verification again. A terminal reservation can be released through the same completion transition once the predecessor's orderly release or verified process exit proves its broker-owned physical work is gone. Provider-retained input is separate: this transition never removes an attempt, receipt, or recipient barrier. Stale readiness and fresh registration cannot bypass barriers belonging to any historical incarnation of the provider conversation.

## Session identity and trust

Canonical identity records include a globally unique session incarnation, project, provider/runtime type, provider conversation ID, user-facing name, broker ownership generation, opaque endpoint binding, capabilities, readiness, and activity times. This replaces name/PPID/TTY watches as the routing source; it is not an additional registry beside them. PID and process-start observations are supplemental diagnostics, not routing keys.

Bootstrap and administration trust the verified local OS user. The broker obtains the peer principal from the connected Unix stream and rejects unavailable or mismatching identity before these operations. An RPC role string, connection name, directory, or PID supplied by a caller cannot establish that principal. Under this policy another process running as the same user can also administer Waggle; no human-only authority is claimed. A second socket or a same-user token would not create that separation. A requirement for human-only administration would require a separately enforced principal boundary and a new design decision.

Preparation allocates a globally unique incarnation and broker-generated random credential over the private channel; only its hash is persisted. Completing bootstrap grants the credential its canonical session scope, and verified native binding permits active use. `--name` selects a label and cannot impersonate a registered sender. Provider account authentication stays inside the provider installation. Claude's messaging token is never transmitted to, stored by, or used by the broker or its driver. Waggle outbound credentials are independent capabilities; there is no reuse or derivation from a native messaging token.

The canonical states are `preparing → pending → bound ↔ disconnected`, with `retired` terminal for an incarnation. `preparing` records an incomplete credential handoff: it cannot authenticate ordinary session commands, receive even an offline enqueue, or initiate provider attachment. `pending` records a completed credential handoff with native verification outstanding; it cannot authenticate as an active sender or receive native input. Initial binding requires that exact pending incarnation before its fixed enrollment deadline. Reverification of a previously bound/disconnected incarnation instead requires the same immutable native binding and surviving, successfully installed private credential scope; it neither reuses the initial deadline nor rotates credentials. All readiness writes require current owner generation, exact incarnation/binding, and a still-valid reservation. Preparing and retired rows cannot bind; a late observation cannot revive retirement.

Expiration moves `preparing` or `pending` to `retired` with a reason distinguishing incomplete handoff from readiness deadline. It cancels eligibility of the affected unsent queue and initiates worker teardown. It does not assert provider termination or input consumption. The `failed` state is removed, not retained as another terminal uniqueness rule. Live label/conversation indexes exclude only `retired`, while capacity counts outstanding reservations until teardown joins. Fresh registration requires a fresh supported SessionStart lifecycle, available capacity, and no historical unresolved barrier for that provider conversation. Changing label, endpoint, secret, or process is not a bypass. Exact late acknowledgements by a previously bound retired incarnation remain valid for its own attempts.

The supported SessionStart hook supplies the native conversation ID and exact endpoint. Once bootstrap is complete and the broker verifies binding and native receive availability, it commits `bound` and can deliver the first message to the idle session. No ordinary tool call, test send, acknowledgement, or human prompt is an activation prerequisite. Readiness arriving after the bounded hook returns completes verification of the same registration. There is no probe message that starts a model turn.

Outbound identity is authenticated independently on every ordinary CLI call using the scoped credential for that bound incarnation. There is no send-active flag or per-session demonstration gate. Missing/invalid credentials fail that call without inventing identity or preventing receipt through an already verified endpoint. Demonstrating credential propagation is a one-time M1 integration-conformance obligation for each supported host/version, not a runtime prerequisite repeated by every session. Endpoint ownership and session binding cannot be inferred from a path or label. Two sessions sharing a directory must not share credentials. This isolates legitimate registered sessions; a fully privileged malicious same-OS-user process is not contained by Unix socket permissions alone.

Claude enrollment passes only the native socket endpoint, provider session identity and Waggle registration material, never `CLAUDE_CODE_MESSAGING_TOKEN`. Its SessionStart environment-file facility is the candidate private credential installation mechanism. Codex requires an explicit private per-thread credential installation facility for ordinary shell tools on the attached TUI. Copying configured environment values into hooks does not implement a hook-to-thread credential return channel. Both mechanisms require M1 evidence of actual host application before first ordinary acknowledgement; process-wide environment, transcript inspection, prompt context, and PID inference cannot substitute.

Initial enrollment occurs only at the supported SessionStart lifecycle event. If the broker was unavailable when that event ran, the hook reports unavailability and the host continues unenrolled. Starting the broker later does not discover or silently enroll that live session. The missing-enrollment error directs the user to start the broker and restart the session through the supported entrypoint so SessionStart runs again.

After a broker restart, persisted sessions begin disconnected/unverified. Only native reconnection to the same explicitly bound endpoint and provider conversation plus observed readiness makes them ready; this restores prior enrollment and requires no demonstration tool call. Broker ownership generations fence stale callbacks. Known provider conversation IDs support exact evidence correlation, not an unspecified recovery operation. Closing a terminal view is distinguished from terminating the provider runtime: reattaching a view to the same loaded native thread uses its existing private scope and enrollment without another preparation. Native initialization after that scope has been lost follows the explicit failure policy below; no claim is made to restore private in-memory state after a process or machine crash.

## Credential preparation, installation, and confirmation

The selected proposal retains broker-generated secrets. It adds a bounded two-RPC bootstrap within the one supported SessionStart invocation. This is an explicit enrollment protocol change and schema revision; it replaces the existing single `Enroll` request rather than adding an optional second path. It does not change the one-attempt message contract.

1. `PrepareEnrollment` verifies the local bootstrap principal, selected complete provider contract, immutable project/conversation/endpoint binding, uniqueness, historical barriers, and reservation capacity in one fenced transaction. It inserts `preparing`, the credential hash, a reservation, and a deadline assigned once from configured enrollment bounds. Only after commit does the response carry the incarnation and its new secret. No worker may attach this preparation. No secret is printed, logged, persisted in the canonical database, or returned by diagnostic queries.
2. The hook installs that credential using the selected host's private incarnation-scoped mechanism. The mechanism must guarantee that subsequent ordinary tools for this exact incarnation receive it, while sibling sessions and newly forked conversations do not. The host applies the staged value as part of successful SessionStart completion. Merely writing a broker-owned file or receiving a successful generic shell command is not sufficient evidence of that host contract.
3. After successful staging, the same hook sends `ConfirmEnrollment`, authenticated with the prepared secret and exact incarnation. A fenced transaction checks the original binding and deadline and changes only `preparing → pending`. It never renews the deadline. Duplicates for the same confirmed, non-retired incarnation return current state without rotating credentials or creating another enrollment. Confirmation after retirement fails. This request establishes completed bootstrap staging, not native readiness or a message receipt.
4. The hook returns. The native host completes its private environment installation and publishes the initialized conversation. The worker can then verify exact membership/readiness and bind the pending enrollment. SessionStart never waits for subscription to a thread whose publication depends on the hook returning. The selected native contract must prevent input execution and ordinary tools from overtaking installation. If a host cannot establish that ordering, its integration remains unsupported.

Failure outcomes are part of this protocol:

- Prepare fails before commit: no preparation or capacity reservation exists.
- Prepare commits but its response is lost: the inactive preparation expires and is retired; no secret is reissued or recovered through another channel. A repeated prepare for that live binding fails explicitly. The host continues unenrolled; a fresh SessionStart after retirement can create a new incarnation. This deliberately chooses bounded failure over secret-recovery machinery.
- Host staging fails or the hook exits before confirmation: the preparation stays inactive until retirement. Any partially staged secret grants no active session authority. No worker can deliver input to it.
- Confirmation fails before commit: the preparation remains inactive. The staged value alone does not grant active scope.
- Confirmation commits but its response is lost: the host already holds the staged secret, and the original registration can finish native verification after the hook returns. The diagnostic reports that confirmation is unknown; it cannot truthfully report definite non-registration. A duplicate confirmation is idempotent, but there is no automatic transport fallback or unbounded hook retry.
- Broker restart between stages: the original preparation/deadline remain canonical; confirmation against the current owner may complete only that still-valid preparation. Confirmed sessions reverify native readiness without replacing credentials. A lost preparation response still cannot be recovered by issuing a different secret.

Confirmation is an assertion from a trusted bootstrap integration, not cryptographic proof that the host installed an environment value. The proof obligation is the pinned native implementation and conformance test of its ordering, failure, and scope behavior. It is not a repeated ordinary-tool demonstration or an acknowledgement gate.

For the custom Codex build, the proposed mechanism is one host-owned staging file created in a private per-thread scope before SessionStart. Its opaque path is passed only to that hook. The bounded, versioned record contains the exact native thread ID, broker incarnation ID, and Waggle credential; the host fixes the destination environment key rather than accepting arbitrary permission/configuration overrides. The host validates the record, installs the credential in that thread's private shell environment, and removes the staging file before native initialization makes Waggle input eligible. The original secret remains available to future shell calls in that live thread; a fork starts with an empty scope. Malformed/missing installation leaves normal host use available but cannot advertise a completed Waggle bootstrap. Native readiness evidence must distinguish successful application from an ordinary loaded thread when application can fail after confirmation. This is a proposed host extension, not an existing capability. Its exact wire field names, native readiness observation, file ownership rules, and failure ordering must be implemented and proved together at M1 before enabling Codex support. Do not infer private installation from `HookRuntimeOutcome.additional_contexts`; prompts and hook context cannot carry the credential.

Claude's existing environment-file candidate must satisfy the same application/scope contract using its supported native behavior; a Waggle-created side file is not a substitute. Whether it provides the required ordering or observable failure behavior is still unconfirmed. A host that cannot meet this contract is a capability blocker, not a reason to reinterpret generic readiness as credential-installation evidence.

The credential survives a broker restart only while its native scope survives. A fork or genuinely new provider conversation requires a fresh incarnation and secret, with no inherited active credential. Native resume that loses the original private scope cannot silently rotate its credential or reuse the old enrollment. The supported initial policy is to fail that enrollment explicitly; historical retained-input barriers still require original correlated evidence. Neither retirement nor native process exit grants a replacement credential authority to acknowledge an old attempt.

The rejected alternative for this revision is host-generated secrets prepared before registration. It simplifies lost-response idempotency but changes credential origin and still requires an unproven private host scope and its fork/resume lifecycle. The selected broker-generated handoff accepts explicit inactive preparations after failure and uses the existing issuer. Do not implement both mechanisms or a fallback between them.

Authorization is command-specific: bootstrap principal for preparation; prepared secret for confirmation; bound session credential for new sends; exact original recipient credential for late consumption; participant credential for conversation stop; verified local operator principal for endpoint registration/replacement, retirement, and broker shutdown. OS authorization governs the subsequent signal that escalates shutdown. Administrative operations cannot fabricate receipts, release retained-input barriers, or impersonate a sender. There is no operator reconciliation mutation in this initial contract. Unsupported commands and malformed or missing credentials fail on the canonical route.

A failure executing that source returns an error; it cannot activate path identity because `WAGGLE_ROOT` happens to exist.

With neither explicit ID nor selector, select Git. Path mode requires a nonempty `WAGGLE_ROOT` and forms exactly the established `path:<value>` identity. Merely setting `WAGGLE_ROOT` in Git mode still does not change identity source. Explicit source selection remains mandatory.

## Message and attempt lifecycle

Extend message storage with canonical sender/recipient session references, conversation ID, reply-to message ID, deadline, deduplication key, and provenance. Existing numeric IDs can remain internal database keys; externally exchanged message/session identifiers must be globally unique. Message text stays untrusted text, with bounded size and explicit peer provenance.

The canonical native delivery envelope carries the message ID, attempt ID, recipient incarnation, conversation/reply correlation, sender provenance and deadline separately from the peer-controlled body. Both drivers preserve these fields. Installed receiver instructions require an ordinary authenticated `waggle ack <message-id>` after consuming the envelope, even when declining its requested work, or a correlated reply that records consumption in the same broker transaction. This instruction comes from the installed integration, not arbitrary text supplied by a peer; it grants no tool permission and does not mean the work completed. The broker accepts only the original recipient's receipt for that attempt. An acknowledgement may record late consumption after stop/deadline without restarting dispatch. If native policy blocks the acknowledgement tool, fail visibly and retain the barrier; do not acknowledge from a hook, transport callback, or inbox read. M1 must prove that the first message supplies everything needed for the first ordinary acknowledgement call.

Each dispatch has one immutable attempt ID, owner/generation, submission intent, and provider reference when observed. Selection and intent commit reserve the recipient barrier before any provider call. The broker applies evidence only to the original attempt and recipient incarnation under current broker ownership. No second attempt is created for a message in the initial contract. Definite non-acceptance is a visible failure; loss after intent is uncertain, even if no actual write is known. Restart schedules only stored work without intent. Reconnection and client message IDs never justify resubmission.

One broker transition function derives scheduling eligibility and user-visible status from durable intent, observed receipt evidence, and the message/conversation stop or deadline disposition. These are different facts, not competing success flags. Inbox and event views are read-only. Transport bytes written, a successful socket close, or provider turn completion without message correlation are not receipts.

Ordering is per recipient incarnation in queue sequence order: at most one Waggle message may be awaiting proof of consumption or non-retention. It is an input-consumption guarantee, not completion ordering for arbitrary tools or human work inside the provider. The barrier has these rules:

- Before intent, a stored message has not left Waggle. Cancellation or expiry prevents intent atomically; removing it from eligibility does not block subsequent eligible messages.
- Intent committed, submission in progress, or unknown result retains the barrier. The provider may already possess input. Process interruption does not release it.
- Native accepted or held evidence retains the barrier. Both mean the provider can still consume the input later. A held outcome is conclusive about retention, not completion.
- Correlated acknowledgement/reply from the exact receiving session proves consumption and releases the barrier. This does not prove that resulting native work has finished. Alternatively, provider evidence specific to this attempt proving refusal, drop, or absence of retained input releases it. A transport rejection proves non-retention only when M1 establishes that meaning.
- Deadline, stop request, native disconnection, and elapsed time cannot release a barrier after intent. Later messages to that incarnation remain visibly blocked by the original message ID. Queue bounds still apply.

Cancellation and deadline behavior are deliberately limited to guarantees the broker controls:

- Before intent, cancellation is confirmed locally and expiry is final for dispatch. A concurrent scheduler must serialize with that transition so only one wins.
- After intent, persist cancellation requested or deadline elapsed and stop all future dispatches in that Waggle conversation, including queued replies. Withdrawal remains unsupported in the initial native contract; if the original submission result is also unknown, report both unsupported withdrawal and uncertain possession. Never label this simply cancelled or safely expired.
- While a provider holds input, approval or a provider settings change may deliver it after Waggle stops. Waggle performs no mode change, automatic resend, or replacement delivery. Retention and its barrier remain until correlated consumption or definitive drop evidence arrives.
- After consumption/acceptance, stopping Waggle stops future Waggle dispatches, not native execution, tools, or effects already initiated. The broker invokes neither Claude session termination nor Codex `turn/interrupt`. Codex exposes turn-level interruption, which cannot establish per-message withdrawal from a turn shared with human input. Native stop remains under the human's ordinary provider controls; any resulting observations must be reconciled for this message before changing retention state.
- Late receipts append evidence to the same attempt and can establish consumption or drop. They never erase the stop/deadline disposition, restart the conversation, reset its budgets, or authorize a resubmission. A late reply is inspectable but does not automatically trigger another reply.

The initial contract has two concrete evidence producers: the original recipient's authenticated `ack`/correlated reply, and the enrollment worker's original correlated native response. The former proves consumption; the latter establishes only the method-specific outcome proved by the pinned provider contract. A supported asynchronous receipt would need its own named native event, exact attempt/incarnation correlation, and conformance evidence before entering that provider's catalog contract. Generic turn completion, empty history, process exit, an operator assertion, or silence is not such an event. A lost response cannot be reconstructed from an error code remembered without its request correlation.

There is no operator `reconcile` command or unspecified retained-input lookup in this revision. An operator can inspect the blocking message/attempt, restore the view of the still-loaded original native thread so that its original credential can acknowledge consumed input, or retire the Waggle incarnation and cancel its unsent queue. Retirement permanently disables that incarnation's routing but neither resolves the retained-input barrier nor cancels native work. Re-enrollment of the same provider conversation remains blocked across all historical incarnations and endpoint bindings until actual consumption/non-retention evidence arrives. A genuinely new provider conversation can enroll without transferring or resubmitting the old queue.

If the native scope and its receipt credential are actually lost, and no correlated native evidence is available, the original conversation may remain permanently unavailable to Waggle. Retirement, restart, deadline, and replacing the endpoint do not recover it. Diagnostics must name the blocking attempt and state that no supported evidence-based recovery exists in that case; they must not recommend a nonexistent reconciliation command. This is an explicit availability limit, not proof of reliable recovery. Removing that limit requires a separately reviewed, provider-supported durable evidence or receipt-authority contract. It cannot be implemented by guessing non-retention or minting a successor credential for the old receipt.

Sending an agent message never approves the recipient's tools or changes its model/sandbox/approval settings. Peer provenance is explicit, and peer-supplied fields cannot become provider permission controls. Conversation deadlines and turn/hop budgets are inherited and decremented by canonical operations. Stop/deadline and exhausted budgets reject new dispatches even if an agent replies late or tries to create a reply with reset metadata. These limits bound Waggle dispatches; they cannot bound arbitrary native execution after delivery.

## Replacement decisions and implementation order

The accepted structure is owner-supervised enrollment workers. A central control loop supervising asynchronous I/O is a credible alternative, but adds mailbox ordering/drain obligations to an already transactional domain. Independent observer/deliverer/reaper loops with a durable attachment bit would additionally require a physical transport generation/handoff protocol. Workers keep that resource coordination local. If the worker design is wrong, its largest risks are missed join obligations and transaction load from many independent observers; configured bounds and the experiments below must address them.

Replace complete boundaries in this order; these are development stages, not runtime compatibility modes:

1. Specify the private native credential installation contract and make incomplete provider composition fail explicitly. Implement the canonical preparing/pending/retired transitions, reservation accounting, and two-RPC bootstrap as one schema/protocol change. No old single-RPC enrollment handler remains as an alternate path. Existing user stores are not converted during this stage.
2. Implement owner registration, publication, separate stop/interruption signals, completion transactions, and deadline-independent finalization. Keep current `Owner.Do` and fenced `Operation.Write` behavior for genuine scoped mutations. Delete the shared shutdown/native-call cancellation context and replace the command's `Serve`-then-shutdown-result sequence with concurrent failure/progress observation.
3. Replace the global scheduler with enrollment workers and recipient-specific transactional selection. Delete `operationState.resources`, `Operation.Open`, `Resource`, `Resource.Use`, the resource-owning scheduler operation, exported generic provider `Handle`/`Open` wrappers, the subscriptions-map handoff before submit, and `nativeBatch` barriers. Move private provider mechanics behind the broker package boundary in the same replacement. A disconnected worker may reconnect its existing binding; it may never replay an intent.
4. Make the single catalog authoritative for installer, hook parser, domain contract selection, and driver dispatch. Delete independent provider allowlists, optional capability flags, and any installer that presents a partial integration as usable. Retain concrete provider-specific parsing and authorized endpoint checks. Replace the per-start endpoint override with the specified register-if-absent/equality-assertion option and explicit operator replacement RPC; no ephemeral endpoint value independently controls a worker.
5. Replace `failed` and its inconsistent capacity counting with retired reasons and reservation release after join. This is part of the schema transition from step 1, not an online repair branch. Delete any durable attachment column proposal. Preserve all historical attempt, barrier, and receipt constraints.
6. Select project identity before resolution, validate metadata on open, and bound the complete command. Delete Git-error-to-path substitution while preserving existing identity strings and paths.
7. Complete and prove one provider's installation → SessionStart → private credential → native receive → first acknowledgement path, then the other. Replace blanket post-write RPC-error classification with the pinned method-specific response rules. Delete the undefined operator-reconciliation promise; no administrative receipt override or speculative history lookup replaces it. Native protocol fixtures cannot enable support. Run full application verification and the original cutover/release milestones only after these replacements.

Do not add a second attempt after `not_submitted`. Definite non-retention can release the old barrier, but the same message still has its immutable attempt. Adding retry limits, backoff, or attempt selection would be a separate product contract and is not part of this correction.

## Revision 6 behavioral acceptance experiments

These are proposed tests, not executed evidence. Deterministic gates must stop execution at the named boundary; sleeps alone do not establish the interleaving. Fakes are appropriate for lifecycle and fault injection. They cannot establish native-host scope or wire semantics.

1. **Registration/publication:** pause worker registration and endpoint construction on both sides of shutdown's linearization point. A losing registration creates nothing. An already-created but unpublished endpoint closes before release. No shared lock prevents immediate admission closure or deadline reporting.
2. **Construction failure:** start a reader, fail the next initialization step, and block its callback. The worker and reservation remain counted until that callback, reader, and connection join. Failed construction cannot disappear from accounting.
3. **Admitted completion:** pause a dispatch after intent with a fake that observes and fails on native-call context cancellation. Begin orderly draining and assert that context remains uncancelled and transport close has not begun; new `Do` calls fail. Release the provider result and verify exact fenced persistence before transport closure. Separately expire the call's own deadline and escalate with a second operator signal: each cancels I/O, records its truthful result, and still joins. Repeat with teardown completion deleting a retired slot through its pre-registered SQL callback. No completion path opens another provider or selects new work.
4. **Join and finalizer failure:** block a closer beyond two separate waiters' deadlines, then release it. Both waiters report incomplete shutdown; admission remains closed; the same finalizer later cleans endpoints and releases without another shutdown request. A later waiter succeeds, while the timed-out foreground command exits nonzero and reports eventual release. A real close error or failed completion transaction instead remains explicit and prevents release, including a contention failure after its configured bound.
